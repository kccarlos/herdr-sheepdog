# Xcode Cloud: TestFlight on every tag

Xcode Cloud only archives the app and uploads it to TestFlight, on an
`ios-v*` tag. **It runs no tests and builds no pull requests.** The tests,
unit and UI, run on GitHub Actions: `.github/workflows/ios.yml` on a
GitHub-hosted Mac, simulator only, no secrets, with fixture daemons built in
the same job ([development.md](../../../docs/dev/development.md#cicd),
[status.md](status.md#running-the-tests)). Until 2026-10-21 a **PR**
workflow also tested every pull request here; it was removed when the tests
moved to GitHub Actions. The app lives in `ios/` of the sheepdog repository (until
2026-10-15 it was the separate `herdr-sheepdog-ios` repository; the switch
of the workflows is in
[xcode-cloud-monorepo.md](../../../docs/dev/xcode-cloud-monorepo.md), and the
old `v*` tags are now `ios-v*`). Xcode
Cloud minutes are included in the Apple Developer Program.

built from tag `ios-v0.1.5` (`b414dda`, #41).

## How the build works

The `.xcodeproj` is generated by XcodeGen and not committed. Xcode Cloud
runs `ci_scripts/ci_post_clone.sh` right after it clones the repository and
before it opens the project, from the `ci_scripts` directory next to where
the project will be ([Writing custom build
scripts](https://developer.apple.com/documentation/xcode/writing-custom-build-scripts);
installing a tool there is Apple's documented way to add build tools,
[Making dependencies available to Xcode
Cloud](https://developer.apple.com/documentation/xcode/making-dependencies-available-to-xcode-cloud)).
The script:

1. `cd "$CI_PRIMARY_REPOSITORY_PATH"`.
2. On a tag build, checks that the tag is `ios-v` + `MARKETING_VERSION` and
   fails otherwise, so a mistyped tag cannot ship a build under the wrong
   version.
3. Gets XcodeGen 2.46.0 from its GitHub release zip (checked against a
   pinned SHA-256; a few seconds), and falls back to `brew install xcodegen`
   if the download fails. Homebrew is on Xcode Cloud's machines, but
   `brew install` there usually takes a minute or two of billed time and
   installs whatever version is current.
4. `xcodegen generate`, then checks that the shared `Sheepdog` scheme
   exists.
5. Checks that `Package.resolved` is in the generated project (XcodeGen's
   `postGenCommand` copies the committed `ios/Package.resolved` there;
   Xcode Cloud does not resolve Swift packages without it), and trusts
   package build-tool plugins (SwiftTerm has one), since nobody can click
   Trust & Enable on Xcode Cloud ([architecture.md](architecture.md#the-terminal-surface)).

It runs once per action (the workflows have a single Archive action).

**Build numbers.** Xcode Cloud numbers its builds 1, 2, 3, … per app, and
when a build goes to TestFlight App Store Connect uses that number as the
build number ([Setting the next build number for Xcode Cloud
builds](https://developer.apple.com/documentation/xcode/setting-the-next-build-number-for-xcode-cloud-builds)).
So nothing sets `CURRENT_PROJECT_VERSION`; it stays `1` for local builds and
the script only logs `CI_BUILD_NUMBER`. Every upload has a new number, and
re-running a failed build is a new build with a new number. To start from a
higher number: App Store Connect ▸ the app ▸ Xcode Cloud ▸ Settings ▸ Build
Number ▸ Edit.

**Signing.** Xcode Cloud signs with cloud-managed certificates for the team
and creates the profiles itself; nothing about signing lives in the
repository or in secrets. Locally, `CODE_SIGN_STYLE: Automatic` with the
same team.

**Push notifications.** The app has two capabilities in its entitlements
(`Sources/Sheepdog/Sheepdog.entitlements`, generated by XcodeGen from
`project.yml`): `aps-environment` — `development` in the Debug
configuration, `production` in Release, which is what Xcode Cloud
archives — and `com.apple.developer.usernotifications.time-sensitive`. The
Info.plist key `SheepdogPushEnvironment` follows the same split (`sandbox` /
`production`) and is what the app tells the daemon its device token belongs
to. Xcode Cloud's automatic signing does **not** turn these capabilities on
for the App ID. Build 9 failed at export with "Automatic signing cannot
update bundle identifier". On 2026-10-02 **Push Notifications** and **Time
Sensitive Notifications** were enabled by hand on the App ID
`com.github.kccarlos.herdr-sheepdog-ios`
(<https://developer.apple.com/account/resources/identifiers/list>), and the
next build shipped. Any new capability needs the same step before the
first archive that uses it.

**The widget extension** (`SheepdogWidgets`, since #37) is embedded in the
app and signed with its own App ID,
`com.github.kccarlos.herdr-sheepdog-ios.widgets`, registered ahead of time
with `asc bundle-ids create` so the archive's automatic signing only has to
make profiles. It has no entitlements: Live Activities need only
`NSSupportsLiveActivities` in the app's Info.plist, and its App Intents run
in the app's process. Simulator builds do not sign, so the first tag archive after #37 (0.1.4 (48)) was the first real check of
this, and it signed and exported with no change.

**The Notification Service Extension** (`SheepdogNotificationService`)
decrypts relay notifications. Its App ID,
`com.github.kccarlos.herdr-sheepdog-ios.NotificationService` (resource
`JTDHJGH486`), was registered with `asc bundle-ids create` on 2026-10-15,
and `asc bundle-ids capabilities add --capability APP_GROUPS` enabled App
Groups on it and on the app's App ID. The App Store Connect API cannot
create the group itself: a local `xcodebuild archive
-allowProvisioningUpdates` with the team's account signed into Xcode
registered `group.com.github.kccarlos.herdr-sheepdog-ios` and assigned it to
both App IDs, and an `app-store-connect` export of that archive signed. By
hand the same is developer.apple.com ▸ Identifiers ▸ App Groups ▸ +, then
App Groups ▸ Configure on both App IDs. On the daemon side, you need an APNs auth key
(`.p8`) for team `GV776BZVA8` (herdr-sheepdog `docs/push.md`).

**Export compliance.** `ITSAppUsesNonExemptEncryption` is `NO` in the app's
Info.plist: the app uses only the encryption built into iOS (HTTPS/WSS
through `URLSession`), which is exempt, and none of its own. Without the key
every build waits at "Missing Compliance" in TestFlight until someone
answers by hand. If the app ever ships its own cryptography, this changes.

## 1. Connect the repository (once, in Xcode on the Mac)

Signed in to Xcode with the Apple ID of the paid team (Xcode ▸ Settings ▸
Accounts). Accept any pending agreement first:
<https://developer.apple.com/account> and
<https://appstoreconnect.apple.com/agreements> — until then Xcode Cloud
onboarding fails with errors that do not always say "agreement".

```sh
cd herdr-sheepdog/ios
git checkout main && git pull
xcodegen generate
open Sheepdog.xcodeproj
```

1. **Integrate ▸ Xcode Cloud ▸ Create Workflow…** (or the Report navigator's
   Cloud tab ▸ Get Started). Xcode Cloud items live under **Integrate**, not
   **Product** — `Integrate ▸ Xcode Cloud ▸ Create Workflow…` /
   `Manage Workflows…`.
2. **Select a product**: choose **Sheepdog** (the app). Next.
3. Xcode shows a default workflow. Edit it into the **TestFlight**
   workflow below (section 2), with no Test action. Next.
4. **Grant access to your source code**: Xcode sees
   `github.com/kccarlos/herdr-sheepdog` and asks for access. Click
   **Grant Access**. The browser opens App Store Connect ▸ **Connect** ▸
   GitHub asks to install the **Xcode Cloud** GitHub App: install it on the
   account `kccarlos`, **Only select repositories** ▸
   `herdr-sheepdog` ▸ Install. Back in Xcode, the repository shows as
   connected. **The remote must be an HTTPS GitHub URL** — see the
   troubleshooting entry below if Xcode Cloud says it cannot find the
   repository.
5. **Connect to App Store Connect**: there is no app record yet, so Xcode
   offers to create one. The name `Sheepdog` was taken on the App Store, so
   the record is named **"Sheepdog for herdr"** instead (only the store
   listing name — the home-screen label stays "Sheepdog"), primary language
   English (U.S.), bundle ID `com.github.kccarlos.herdr-sheepdog-ios` (Xcode
   registers it on the team if it is not yet registered). **Complete**. The
   record is App ID 6817155887, SKU `herdr-sheepdog-ios`.
6. Xcode starts the first build. Watch it in the Report navigator ▸ Cloud.

Workflows are stored in App Store Connect, not in this repository. Edit them
in Xcode (Report navigator ▸ Cloud ▸ right-click **Sheepdog** ▸ Manage
Workflows…) or on the web (App Store Connect ▸ the app ▸ Xcode Cloud ▸
Manage Workflows).

## 2. The workflows

There are two, both archive-only. Neither has a Test action, and neither
starts on a pull request or a branch push. Keep it that way: tests belong in
`ios.yml`.
(Checked with `asc xcode-cloud workflows` on 2026-10-21: **TestFlight**, tag
prefix `ios-v`, one Archive action; **Internal TestFlight Build**, manual
start only, one Archive action.)

### TestFlight

| Section | Setting |
|---|---|
| General | Name `TestFlight` |
| Environment | Xcode **Latest Release**, macOS **Latest Release** |
| Start Conditions | **Tag Changes**: Custom Tags ▸ tag begins with `ios-v` (plain `v*` tags are daemon releases). Remove any branch condition |
| Actions | **Archive** ▸ Platform iOS, Scheme **Sheepdog**, Deployment Preparation **TestFlight and App Store** (the API shows `APP_STORE_ELIGIBLE`; external testing needs it) |
| Post-Actions | **TestFlight External Testing** ▸ group **Public**, and **TestFlight Internal Testing** ▸ group **Me** (section 4) |

The post-actions need their groups to exist, so create them (section 4)
before adding them.

### Internal TestFlight Build

Xcode auto-creates this third workflow the first time a product is set up
for distribution (it appeared alongside PR and TestFlight without being
asked for). It starts manually on a branch — there is no automatic Start
Condition — and its builds are **not** added to any TestFlight group by
Xcode Cloud; add a build from it in App Store Connect ▸ TestFlight ▸ **Me**
▸ Builds ▸ **+** if one is needed. In practice the **TestFlight** workflow
(tag-triggered) is the one used to ship; this one is left as Xcode made it.

## 3. What it costs

The Apple Developer Program includes **25 Xcode Cloud compute hours a
month**, at no extra charge; paid plans add more hours, and nothing is
billed unless you subscribe to one. Usage is in App Store Connect ▸ Users
and Access ▸ Xcode Cloud, or on <https://developer.apple.com/account> ▸
Xcode Cloud. Compute time counts per action, including the post-clone
script.

Expected, from this repository on a local Mac (Xcode 27, Apple silicon;
Xcode Cloud machines are in the same range but a clean build every time):

- **TestFlight** (post-clone + Release archive + signing + upload): about
  5–10 minutes, then App Store Connect processes the build for another
  5–30 minutes (not billed) before TestFlight offers it.

So 25 hours is on the order of 150–300 releases a month; pull requests cost
nothing here, since their tests run on GitHub Actions.

## 4. TestFlight, once

1. App Store Connect ▸ Apps ▸ **Sheepdog** ▸ **TestFlight** ▸ **Internal
   Testing** ▸ **+** ▸ group name `Me`, turn on **automatic distribution**
   ▸ Create.
2. In the group ▸ **Testers ▸ +** ▸ add your own Apple ID (the Account
   Holder is already a user of the team; others need to be added in Users
   and Access first).
3. TestFlight ▸ **Test Information**: a feedback email is enough for
   internal testing (external testing also asks for a description and a
   beta review contact).
4. On the iPhone: install **TestFlight** from the App Store and sign in with
   the same Apple ID. When a build lands, TestFlight notifies and offers
   **Install**.

Internal testers get builds without App Review, so the app's
`NSAllowsArbitraryLoads` (plain HTTP to the daemon on your own network)
needs no justification for this. External testers or the App Store would.

## 5. Releasing a build

```sh
# project.yml: MARKETING_VERSION: "0.1.1" (bump it in a PR first: the next release is 0.1.2 or 0.2.0)
git checkout main && git pull
git tag ios-v0.1.1   # the tag must be ios-v + MARKETING_VERSION and unused
git push origin ios-v0.1.1
```

The TestFlight workflow starts on the tag, archives, uploads, and adds the
build to the `Me` group; TestFlight shows it as `0.1.1 (N)` with `N` the
Xcode Cloud build number. A tag is used once: for the next build, bump
`MARKETING_VERSION` (e.g. to `0.1.2`) and tag `ios-v0.1.2`. To send another
build of the same version instead, start the TestFlight workflow by hand in
Xcode (Report navigator ▸ Cloud ▸ right-click TestFlight ▸ Start Build ▸
branch `main`); it gets a new build number, and a manual start on a branch
skips the tag check.

## 6. When something fails

To see why a run failed without opening Xcode, use `asc xcode-cloud doctor`
and download the log artifacts (`~/.claude/skills/asc/SKILL.md`).

| Symptom | Cause | Fix |
|---|---|---|
| Fails in "Run ci_post_clone.sh" with `tag ios-vX does not match MARKETING_VERSION` | the tag and `project.yml` disagree | delete the tag (`git push --delete origin ios-vX`), fix `MARKETING_VERSION` on `main`, tag again |
| Fails in "Run ci_post_clone.sh" with a download or `shasum` error, then a Homebrew error | GitHub or Homebrew unreachable from Xcode Cloud | re-run; if it persists, check `XCODEGEN_VERSION`/`XCODEGEN_SHA256` in the script against the release |
| `xcodegen` errors in the post-clone log | `project.yml` does not generate | run `xcodegen generate` locally; the same error shows |
| Post-clone script not run at all ("Could not find Sheepdog.xcodeproj") | the script is not executable or not at `ci_scripts/ci_post_clone.sh` | `git update-index --chmod=+x ios/ci_scripts/ci_post_clone.sh`, keep the directory in `ios/` next to `project.yml` and the generated project |
| "Scheme Sheepdog is not shared" / the scheme is missing in the workflow editor | the scheme came from a hand-made project, or `schemes:` was removed from `project.yml` | keep the `schemes:` block; XcodeGen writes it to `Sheepdog.xcodeproj/xcshareddata/xcschemes/`. Regenerate locally and reopen the workflow editor |
| `No profiles for 'com.github.kccarlos.herdr-sheepdog-ios'` / `Automatic signing is disabled` / "requires a development team" | the bundle ID is not registered on team `GV776BZVA8`, or `DEVELOPMENT_TEAM` changed | check <https://developer.apple.com/account/resources/identifiers/list>; register it by hand if onboarding did not; keep `DEVELOPMENT_TEAM: GV776BZVA8` and `CODE_SIGN_STYLE: Automatic` |
| Export fails with "Automatic signing cannot update bundle identifier" (build 9), or the archive fails because the profile "doesn't include the aps-environment entitlement" / "doesn't support the Push Notifications capability" (or Time Sensitive Notifications) | the App ID does not have the capability; Xcode Cloud will not add it | enable Push Notifications and Time Sensitive Notifications on `com.github.kccarlos.herdr-sheepdog-ios` in the developer portal (Identifiers), then re-run ("How the build works" ▸ Push notifications) |
| Signing fails with an agreement or "Program License Agreement" message | a pending agreement | accept it (section 1) and re-run |
| `No suitable application records were found` | no App Store Connect app record | create it (App Store Connect ▸ Apps ▸ + ▸ New App, the bundle ID above) |
| Build sits at "Missing Compliance" | `ITSAppUsesNonExemptEncryption` missing from the built Info.plist | it is in `project.yml`; check it survived an edit |
| The TestFlight post-action has no group to pick | no internal group yet | section 4, then edit the workflow |
| "No source code repositories were found for this project" when connecting the repository | `origin` used the SSH host alias `git@github-kccarlos:…` (an `~/.ssh/config` `Host` alias for a multi-account setup); Xcode Cloud can't resolve it, and a git `url.<alias>.insteadOf` rewrite doesn't help — Xcode applies the remote URL as written | point `origin` at plain HTTPS: `git remote set-url origin https://github.com/kccarlos/herdr-sheepdog.git`, then `gh auth setup-git` (with `gh` logged in as `kccarlos`) so git's credential helper handles push/pull without the SSH alias |
| Yellow warning in the workflow editor: "the scheme Sheepdog may only exist locally and may not be accessible to Xcode Cloud" | expected — `Sheepdog.xcodeproj` is gitignored, so Xcode Cloud can't see the scheme in the repository itself | ignore it; `ci_scripts/ci_post_clone.sh` generates the project (and the scheme with it) on the runner before the scheme is needed |
