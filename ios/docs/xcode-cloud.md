## How the build works

The `.xcodeproj` is generated by XcodeGen and not committed. Xcode Cloud
runs `ci_scripts/ci_post_clone.sh` right after it clones the repository and
before it opens the project, from the `ci_scripts` directory next to where
the project will be ([Writing custom build
scripts](https://developer.apple.com/documentation/xcode/writing-custom-build-scripts);
installing a tool there is Apple's documented way to add build tools,
[Making dependencies available to Xcode
Cloud](https://developer.apple.com/documentation/xcode/making-dependencies-available-to-xcode-cloud)).
The script:

1. `cd "$CI_PRIMARY_REPOSITORY_PATH"`.
2. On a tag build, checks that the tag is `v` + `MARKETING_VERSION` and
   fails otherwise, so a mistyped tag cannot ship a build under the wrong
   version.
3. Gets XcodeGen 2.46.0 from its GitHub release zip (checked against a
   pinned SHA-256; a few seconds), and falls back to `brew install xcodegen`
   if the download fails. Homebrew is on Xcode Cloud's machines, but
   `brew install` there usually takes a minute or two of billed time and
   installs whatever version is current.
4. `xcodegen generate`, then checks that the shared `Sheepdog` scheme
   exists.

It runs once per action (the Test and Archive actions each get a fresh
machine).

**Build numbers.** Xcode Cloud numbers its builds 1, 2, 3, … per app, and
when a build goes to TestFlight App Store Connect uses that number as the
build number ([Setting the next build number for Xcode Cloud
builds](https://developer.apple.com/documentation/xcode/setting-the-next-build-number-for-xcode-cloud-builds)).
So nothing sets `CURRENT_PROJECT_VERSION`; it stays `1` for local builds and
the script only logs `CI_BUILD_NUMBER`. Every upload has a new number, and
re-running a failed build is a new build with a new number. To start from a
higher number: App Store Connect ▸ the app ▸ Xcode Cloud ▸ Settings ▸ Build
Number ▸ Edit.

**Signing.** Xcode Cloud signs with cloud-managed certificates for the team
and creates the profiles itself; nothing about signing lives in the
repository or in secrets. Locally, `CODE_SIGN_STYLE: Automatic` with the
same team.

**Push notifications.** The app has two capabilities in its entitlements
(`Sources/Sheepdog/Sheepdog.entitlements`, generated by XcodeGen from
`project.yml`): `aps-environment` — `development` in the Debug
configuration, `production` in Release, which is what Xcode Cloud
archives — and `com.apple.developer.usernotifications.time-sensitive`. The
Info.plist key `SheepdogPushEnvironment` follows the same split (`sandbox` /
`production`) and is what the app tells the daemon its device token belongs
to. Xcode Cloud's automatic signing does **not** turn these capabilities on
for the App ID. Build 9 failed at export with "Automatic signing cannot
update bundle identifier". On 2026-10-02 **Push Notifications** and **Time
Sensitive Notifications** were enabled by hand on the App ID
`com.github.kccarlos.herdr-sheepdog-ios`
(<https://developer.apple.com/account/resources/identifiers/list>), and the
next build (10) shipped. Any new capability needs the same step before the
first archive that uses it. On the daemon side, you need an APNs auth key
(`.p8`) for team `GV776BZVA8` (herdr-sheepdog `docs/push.md`).

**Export compliance.** `ITSAppUsesNonExemptEncryption` is `NO` in the app's
Info.plist: the app uses only the encryption built into iOS (HTTPS/WSS
through `URLSession`), which is exempt, and none of its own. Without the key
every build waits at "Missing Compliance" in TestFlight until someone
answers by hand. If the app ever ships its own cryptography, this changes.

## 2. The three workflows

### PR

| Section | Setting |
|---|---|
| General | Name `PR`. Restrict editing: off. Repository: `kccarlos/herdr-sheepdog-ios`. Project: `Sheepdog.xcodeproj` |
| Environment | Xcode version **Latest Release**, macOS version **Latest Release**. Clean: off |
| Start Conditions | **Pull Request Changes**: source branch Any, target branch `main`. Add a second one: **Branch Changes**: custom branch `main`. Leave "Auto-cancel builds" on |
| Actions | **Test** ▸ Platform iOS, Scheme **Sheepdog**, Test Plan "Use Scheme Settings", Destination **iOS Simulator ▸ one recent iPhone (e.g. iPhone 17 Pro), Latest Release** |
| Post-Actions | none |

A Test action builds for testing before it tests, so a separate Build action
would only spend minutes. One simulator instead of "Recommended iPhones"
keeps each run to one device. Xcode Cloud reports the result on the pull
request as a GitHub check.

### TestFlight

| Section | Setting |
|---|---|
| General | Name `TestFlight` |
| Environment | Xcode **Latest Release**, macOS **Latest Release** |
| Start Conditions | **Tag Changes**: Custom Tags ▸ tag begins with `v`. Remove any branch condition |
| Actions | **Archive** ▸ Platform iOS, Scheme **Sheepdog**, Deployment Preparation **TestFlight (Internal Testing Only)** |
| Post-Actions | **TestFlight Internal Testing** ▸ group **Me** (section 4) |

"TestFlight (Internal Testing Only)" skips the App Store checks that only
matter for external testers and the store; switch it to "TestFlight and App
Store" if the app ever goes further. The post-action needs the internal
group to exist, so create the group (section 4) before adding it.

### Internal TestFlight Build

Xcode auto-creates this third workflow the first time a product is set up
for distribution (it appeared alongside PR and TestFlight without being
asked for). It starts manually on a branch — there is no automatic Start
Condition — and its builds are **not** added to any TestFlight group by
Xcode Cloud; add a build from it in App Store Connect ▸ TestFlight ▸ **Me**
▸ Builds ▸ **+** if one is needed. In practice the **TestFlight** workflow
(tag-triggered) is the one used to ship; this one is left as Xcode made it.

## 3. What it costs

The Apple Developer Program includes **25 Xcode Cloud compute hours a
month**, at no extra charge; paid plans add more hours, and nothing is
billed unless you subscribe to one. Usage is in App Store Connect ▸ Users
and Access ▸ Xcode Cloud, or on <https://developer.apple.com/account> ▸
Xcode Cloud. Compute time counts per action, including the post-clone
script.

Expected, from this repository on a local Mac (Xcode 27, Apple silicon;
Xcode Cloud machines are in the same range but a clean build every time):

- **PR** (post-clone, build for testing, and the unit tests; the UI tests
  and live-daemon tests skip): about 5–10 minutes. The tests themselves
  take about 1.5 minutes.
- **TestFlight** (post-clone + Release archive + signing + upload): about
  5–10 minutes, then App Store Connect processes the build for another
  5–30 minutes (not billed) before TestFlight offers it.

So 25 hours is on the order of 150–300 runs a month. A PR that is pushed
to five times costs five runs, plus one on merge.

   Testing** ▸ **+** ▸ group name `Me`, turn on **automatic distribution**
   ▸ Create.
2. In the group ▸ **Testers ▸ +** ▸ add your own Apple ID (the Account

3. TestFlight ▸ **Test Information**: a feedback email is enough for

Internal testers get builds without App Review, so the app's
`NSAllowsArbitraryLoads` (plain HTTP to the daemon on your own network)
needs no justification for this. External testers or the App Store would.

## 5. Releasing a build

```sh
# project.yml: MARKETING_VERSION: "0.1.0" (bump it in a PR first for later releases)
git checkout main && git pull
git tag v0.1.0
git push origin v0.1.0
```

The TestFlight workflow starts on the tag, archives, uploads, and adds the
build to the `Me` group; TestFlight shows it as `0.1.0 (N)` with `N` the
Xcode Cloud build number. A tag is used once: for the next build, bump
`MARKETING_VERSION` (e.g. to `0.1.1`) and tag `v0.1.1`. To send another
build of the same version instead, start the TestFlight workflow by hand in
Xcode (Report navigator ▸ Cloud ▸ right-click TestFlight ▸ Start Build ▸
branch `main`); it gets a new build number, and a manual start on a branch
skips the tag check.

## 6. When something fails

To see why a run failed without opening Xcode, use `asc xcode-cloud doctor`
and download the log artifacts (`~/.claude/skills/asc/SKILL.md`).

| Symptom | Cause | Fix |
|---|---|---|
| Fails in "Run ci_post_clone.sh" with `tag vX does not match MARKETING_VERSION` | the tag and `project.yml` disagree | delete the tag (`git push --delete origin vX`), fix `MARKETING_VERSION` on `main`, tag again |
| Fails in "Run ci_post_clone.sh" with a download or `shasum` error, then a Homebrew error | GitHub or Homebrew unreachable from Xcode Cloud | re-run; if it persists, check `XCODEGEN_VERSION`/`XCODEGEN_SHA256` in the script against the release |
| `xcodegen` errors in the post-clone log | `project.yml` does not generate | run `xcodegen generate` locally; the same error shows |
| Post-clone script not run at all ("Could not find Sheepdog.xcodeproj") | the script is not executable or not at `ci_scripts/ci_post_clone.sh` | `git update-index --chmod=+x ci_scripts/ci_post_clone.sh`, keep the directory at the repository root next to `project.yml` |
| "Scheme Sheepdog is not shared" / the scheme is missing in the workflow editor | the scheme came from a hand-made project, or `schemes:` was removed from `project.yml` | keep the `schemes:` block; XcodeGen writes it to `Sheepdog.xcodeproj/xcshareddata/xcschemes/`. Regenerate locally and reopen the workflow editor |
| `No profiles for 'com.github.kccarlos.herdr-sheepdog-ios'` / `Automatic signing is disabled` / "requires a development team" | the bundle ID is not registered on team `GV776BZVA8`, or `DEVELOPMENT_TEAM` changed | check <https://developer.apple.com/account/resources/identifiers/list>; register it by hand if onboarding did not; keep `DEVELOPMENT_TEAM: GV776BZVA8` and `CODE_SIGN_STYLE: Automatic` |
| Export fails with "Automatic signing cannot update bundle identifier" (build 9), or the archive fails because the profile "doesn't include the aps-environment entitlement" / "doesn't support the Push Notifications capability" (or Time Sensitive Notifications) | the App ID does not have the capability; Xcode Cloud will not add it | enable Push Notifications and Time Sensitive Notifications on `com.github.kccarlos.herdr-sheepdog-ios` in the developer portal (Identifiers), then re-run ("How the build works" ▸ Push notifications) |
| Signing fails with an agreement or "Program License Agreement" message | a pending agreement | accept it (section 1) and re-run |
| `No suitable application records were found` | no App Store Connect app record | create it (App Store Connect ▸ Apps ▸ + ▸ New App, the bundle ID above) |
| Build sits at "Missing Compliance" | `ITSAppUsesNonExemptEncryption` missing from the built Info.plist | it is in `project.yml`; check it survived an edit |
| The TestFlight post-action has no group to pick | no internal group yet | section 4, then edit the workflow |
| Tests pass locally, fail on Xcode Cloud in the UI tests | a fixture daemon answered on 127.0.0.1:7799 locally | on Xcode Cloud they should skip; look for a test that does not call `XCTSkip` without a daemon |
| "No source code repositories were found for this project" when connecting the repository | `origin` used the SSH host alias `git@github-kccarlos:…` (an `~/.ssh/config` `Host` alias for a multi-account setup); Xcode Cloud can't resolve it, and a git `url.<alias>.insteadOf` rewrite doesn't help — Xcode applies the remote URL as written | point `origin` at plain HTTPS: `git remote set-url origin https://github.com/kccarlos/herdr-sheepdog-ios.git`, then `gh auth setup-git` (with `gh` logged in as `kccarlos`) so git's credential helper handles push/pull without the SSH alias |
| Yellow warning in the workflow editor: "the scheme Sheepdog may only exist locally and may not be accessible to Xcode Cloud" | expected — `Sheepdog.xcodeproj` is gitignored, so Xcode Cloud can't see the scheme in the repository itself | ignore it; `ci_scripts/ci_post_clone.sh` generates the project (and the scheme with it) on the runner before the scheme is needed |
