## The lesson from three turns of the voice layer (CEO, 2026-10-04)

1. **v1 started as two brains** — and the voice model "said nonsense": it had seven action tools and too little context, so the weaker judge held the side effects (docs/history/issues-2026-09-18.md).
2. **Then the voice model became a mouthpiece** — and it turned out to have its own ideas anyway (answering from memory, "On it.", relaying pushes back).
3. **Then guardrails were added to restrain it** — and that overshot into code that interprets intent.

The gap was never "too much or too little trust in one place"; it is that the harness must **trust the models' judgment as the core** and do two things only: prevent runaways, and **when something happens, put an update into the model's context saying what happened, where it came from, and how it relates to what came before**. Claude Code's own harness is the model to copy: when another agent relays a message, the harness wraps it with a note that it came from an agent, not the user, and is reference only; the model chooses priority (now/next/later) and decides what to do with it. Sheepdog's equivalents: every briefing to the fast brain and every event to the slow brain carries provenance (who: CEO / brain / worker / daemon / another agent), time, and its relation to earlier items (answers your question from 12:03; supersedes the status at 12:01; the CEO heard only the first half; this is the 2nd reminder about the same prompt). The difference from v1 is structural: the fast brain still has no action tools, and it now gets rich, labelled context instead of scripts.

### Result (2026-10-04, #134 #135 #136; details in docs/research/live-resume-context-2026-10-04.md)

None of the four suspects. **A resumption handle issued by a connection that was itself resumed restores only what was said on that connection, not the context it inherited.** The first resume of a session is lossless; every later one keeps only the last connection's content (canary chain arm: 9 of 9 runs, 1,444 → 364 tokens, 0/8 facts recalled; both modalities collapse; later handles and `transparent` do not help). The daemon's logs agree: 7 first resumes ratio 1.00–1.35, 23 later resumes median 0.73. Separately, past the 16k compression trigger the oldest facts are dropped with or without a resume (1/9). Reproducer: `go run ./cmd/livecanary -arm chain -chain-fill 0 -chain-talk`. Options for the CEO (none implemented): (1) never resume a resumed session — start fresh and re-seed from recap and briefings at each later GoAway; (2) resume once, re-seed on the second; (3) leave it and rely on hand-off to the slow brain; (4) report to Google with the reproducer, meanwhile 1 or 2.

## Evals first (CEO, 2026-10-05) — current priority

The harness is judged by two things: does it help the user understand (answers good enough that they get it), and does it get things done. The evals do not measure that well yet (A/B differences need ~70 runs to show; ~40 % of failures were judge or simulated-user artefacts; one rubric item pushes the models the wrong way). So: build the eval suite to cover every dimension first, then use it to drive harness iteration. Meanwhile change the harness only for clear bugs; no prompt tuning except the unified-roles/detail work (#155, not merged), which becomes the new suite's first user. All of this is measurement: no product rule reacts to it.

**Rubric item that rewards laziness:** `internal/eval/sim.go` `ear_friendly` says "short by default (longer only when the CEO asked for detail)", and no default item fails a too-thin answer (`answered` passes when the key facts arrive even with reasons, examples and numbers dropped). Replace it with a two-sided item: length fits the content (short for simple acknowledgements, the full substance when the briefing has reasons, examples or numbers); too thin and too long both fail. Rule for every rubric item from now on: state the failure in both directions.

**North star (top of every report):** 1. Understood — questions answered correctly and in enough depth to understand. 2. Done — the task reached its intended end state, checked against the world, not the transcript. 3. Low effort — few turns, no repeating or rephrasing by the user, reasonable time. 4. Safe — no action beyond the user's words. Everything else is a diagnostic under these four.

**Design — one run measures many things:** (1) workday sessions: 5–8 scenarios of 15–30 min, several workers, the user interleaving status, explanations, "more detail", "why", approvals, instructions, interruptions and a language switch, with one or two forced resumes; one run yields answered, depth, missed news, coherence, said-vs-done, user effort, resume retention; short cases stay as regression tests. (2) Layers on the same record: programmatic checks (said-vs-done: every "sent / stopped / verified / done" claim matched to an action event and outcome; missed news: finished/blocked/result events never told; tier-3 end state; latency, turns, cost); a judge with one call per transcript segment scoring all items, each with a quoted piece of transcript as evidence; pairwise judging (A vs B) for style dimensions such as depth and tone when comparing arms, pass/fail kept for safety. (3) Same scenario in tier 1 and tier 2: the gap is the voice layer's loss. (4) Orchestrator text and voice speech scored separately. (5) Simulated-user personas (terse, rambling, Chinese only, impatient, vague). (6) Real sessions feed the scorecard and become regression cases (as phone-2026-10-04.json started).

**Dimensions to add:** proactivity (missed-news rate; next step offered where it fits); coherence over a long session ("the earlier one", "what did we discuss first", across resumes); said vs done; real end state in tier 3; user effort (turns to goal, repeats, rephrasings); clarification in both directions (asks when genuinely ambiguous, not when clear); adversarial safety beyond bench-injection-screen (worker output trying to get keys sent or an approval made, fake system text on screen, dangerous commands); scale (5–10 workers, clustered events, priorities, names).

**Trustworthy numbers:** judge calibration first (the CEO labels 20–30 transcripts; measure judge–CEO agreement per item; fix items that disagree before scaling); enough repeats with confidence intervals (2 runs per scenario is noise); a held-out set never used for prompt tuning.
