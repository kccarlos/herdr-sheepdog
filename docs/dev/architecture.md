# Architecture

An orientation to the code **as built at `main`**. The contract it
implements (the user / voice / workers, the one rail, stop, pushes,
investigations) is [`docs/dev/roles.md`](roles.md); what is done and what is
open is [`docs/dev/status.md`](status.md). Where this page and `roles.md`
differ, `roles.md` is the intent and this page is what runs today.

## Diagram

```
┌─────────────────────────────────────────────────────────────┐
│  Browser /voice or the iOS app (mic → 16 kHz PCM → WS → 24 kHz → speaker)
│  Browser /debug   (SSE tail of the event log, orchestrator/context views)
└───────────────┬─────────────────────────────────────────────┘
                │ WebSocket (audio bytes + a few control JSON msgs)
┌───────────────▼─────────────────────────────────────────────┐
│  sheepdog daemon (Go, single binary)                         │
│                                                              │
│   VoiceSession ──── Gemini Live (AI Studio/Vertex) or GPT-Live│
│        │ 2 tools + push                                      │
│   Supervisor ── state table ── event log (JSONL) ── SSE      │
│        │  │           │                                      │
│        │  └─ orchestrator (Gemini/Vertex/DeepSeek, tools, history)  │
│   herdr client   prompt parser (code, no model)              │
│   (unix socket)  CLI query tool (codex exec / claude -p,     │
│        │          read-only, timeout)                        │
└────────┼─────────────────────────────────────────────────────┘
         │ ~/.config/herdr/herdr.sock          APNs → iOS app (push)
   herdr ── worker agents (Codex / Claude Code / … in panes)
```

Three layers, hard boundaries:

| Layer | Owns | Never does |
|---|---|---|
| Voice model (Gemini Live or GPT-Live) | hearing, speaking, turn-taking, judging the *moment*; two tools — `to_supervisor(text)` relays the user's words verbatim, `stop()` runs the stop procedure | classify intent, name an agent, touch herdr, hold task state, plan multi-step work (docs/dev/roles.md "One decision-maker") |
| Supervisor (daemon) | state table, pending action, event routing, tool implementations, all model calls that are not voice; its orchestrator (`internal/brain`, [`docs/dev/roles.md`](roles.md)) reasons over the transcript with tools, one turn per user utterance (`to_supervisor`) or worker event | speak; bypass a worker's approval gate (the one rail: `send_keys` only on the user's words, from the prompt's option set) |
| Workers (herdr panes) | actually changing code; their own approval prompts | — |

The voice session lives in the daemon, not the client; the browser or
app is an audio pipe. herdr feeds the daemon over its unix socket
subscription; `POST /api/herdr/event` is a second way in for the same
`herdr.Watcher` (another process, or `/debug`), not something herdr
needs configuring for.

## Context capture

The `/debug` **Context** tab shows, side by side, what each model is
given: on the left the orchestrator's exact request at a model call, on the
right the voice model's context. Both panes use one shape (package
`internal/ctxcap`): the raw text as the model receives it, a section map
over it (sorted, contiguous byte ranges that cover the text exactly),
the provider-native body, estimated tokens per section (4 characters a
token), and a diff against the previous point of the same pane.

**Orchestrator.** After every model call the loop records the step
(`Brain.Requests()`, a `ctxcap.BrainLog`): turn, step within the turn,
kind, provider/model, time, duration, the provider's usage when it
returned, and the request. The body is the chat completions JSON exactly
as sent for an OpenAI-compatible provider (DeepSeek, built by the same
code path — `requestFor` — and compared field for field with the request
an httptest endpoint received), and `{model, contents, config}` as the
daemon handed it to the SDK for Gemini (the SDK owns the wire bytes).
The section map comes from tracing `toContents` / `messagesOf` (the one
implementation of each, with an optional origin callback): a `meta`
section (model, thinking, tool choice), one section per system prompt
section (`role (SOUL.md)`, `tools`, `intent`, `record`, `promises`,
`announcing`, `rail`, `fallback`, `contract`, `USER.md`, the engine's
addition), one per tool
declaration, then every window message by kind (user utterance,
voice said, request — the turn's own marked `current`, a daemon nudge,
orchestrator tool call, orchestrator tool result, push, worker event, promise, note,
daemon note, compaction summary, pruned stub), then the state block —
the last message of every request, cut into `roster`, `ledger`,
`investigations` and `time` (docs/dev/iteration-2.md WP5: the system message
holds only the prompt files, so the provider's prefix cache covers the
system prompt, the tools and the conversation) — with worker output inside
the provenance delimiters cut out as its own `untrusted` piece. DeepSeek's
replayed `reasoning_content` (the current turn's only) is part of the
body and of the pane's estimate, but not of the window estimate
(`brain.window_tokens`), which counts message content only (CONFIG.md
`[deepseek]`). The tab's
"messages / window" line counts the rendered text (timestamps, role
headers, call JSON), so it runs a little higher than the Supervisor
meter's window estimate. The last 200 steps
stay in memory; every step is also appended to
`<data_dir>/brain/<run>.requests.jsonl` (one file per daemon run, a
`segment` field naming the transcript segment, which a "New
conversation" changes), and a restart loads the tail of the newest file,
numbering on from it. Nothing is redacted: the bodies hold no key (a test
asserts it).

**Voice.** Both live models keep their context server-side and it cannot
be read back, so the right pane is reconstructed from what the daemon
sent, and says so. Each provider wraps its connection in a recorder
(`capture.go`) that sees every message in wire order — Gemini's sends
all run under `sendMu`, GPT-Live's through one `Send` — plus what the
model produced that stays in its context. A `ctxcap.VoiceLog` (one per
daemon, each provider session a `VoiceSession`) holds the items: the
session opening (Gemini's setup with its system instructions and tools on
a fresh connection, a "resumed" marker on a resumed one; GPT-Live's
`session.start` with its instructions, the client-delegation setting and
its input items: the recap and the silent context held in standby),
microphone audio as `🎤 audio 3.2 s` placeholders (durations, never
bytes; GPT-Live's keep-alive silence folds into them) with what the model
heard of it, typed text, the model's output transcript, tool calls /
delegations and the responses sent back (with their scheduling), pushes
(`[system event…]` / `[system context…]` client content on Gemini;
commentary / thinking / instructions appends on GPT-Live), and markers
for session close, conversation reset, cancelled tool calls and a
provider switch. An epoch is one context: every fresh session starts
one; a turn point opens at each input the model reacts to (an utterance,
a tool response, a push, a marker). With `--voice=off` the /debug text
router and the skipped pusher record into a `text-router` session
instead, labelled as not reaching any model.

**Links.** Pieces that exist in both panes share a link id:
`call:<voice tool call id>` on the voice's tool call, its response and
the utterance it relayed (claimed when the call arrives), and on the
orchestrator's request for that turn (`Request.Link`), with the turn's tool
calls, results and reply; `push:<id>` minted by `Supervisor.pushTagged`
(tag `push_id`) on the voice push and the orchestrator's push message;
`evt:<id>` minted per herdr transition on the orchestrator's worker event, the
announce turn's request and every push about that event (tag
`event_id`); a late reply's push also carries its call (`call_id`). A
user utterance in the orchestrator's window takes the call link of the
request that relayed it.

**API** (loopback only, like the rest of the debug routes):

- `GET /api/context/brain?step=<n|latest>` → `{step: {step, run,
  segment, turn, turn_step, kind, trigger, agent, provider, model, ts,
  format, forced, window_tokens, tokens, usage, error, dur_ms}, source:
  "exact request", sections: [{key, label, class, group, start, end,
  tokens, path, role, seq, links, pruned, current, text}], body, tokens:
  {<class>: n, total}, diff}`; 404 before the first call or past the
  ring, 503 when the orchestrator is off.
- `GET /api/context/voice?turn=<n|latest>` → `{turn: {turn, ts, epoch,
  session, provider, kind, label, first}, source: "reconstructed from
  what the daemon sent", evicted, sections (with `raw`: the outbound
  message), tokens, diff}`.
- `GET /api/context/timeline` → `{brain: [step metadata], voice: [turns],
  window_tokens, brain_off, voice_off}`, oldest first, for the scrubber
  to interleave by time.
- `diff` is `{prev, added, changed, pruned, compacted, removed: [{key,
  label, class, reason: compacted|reset|removed, text}]}`, by section
  key against the previous point of that pane; a different run or
  transcript segment (restart, reset) or voice epoch between the two
  makes what is gone `reset`.
- A `context.step` event (source `brain`, payload `pane: brain, step,
  turn, turn_step, kind, tokens`; source `voice`, payload `pane: voice,
  turn, kind, session, updated`) is logged at every recorded step or
  turn (and when a voice turn's model output completes), so the tab
  follows live over `/events`.

**Limits.** The voice pane cannot show what the provider did with the
context: Gemini's sliding-window compression, what a resumed session
still holds, or GPT-Live's own truncation are invisible; output audio is
represented by its transcript; token counts are estimates of the text
sent (audio is not counted). Capture is synchronous but cheap (one render
per model call, one mutex per voice item); the tab fetches and renders
only while it is shown.

## Observers

Observers derive something from the event log without touching the
main path (the Pipecat observer pattern). `eventlog.Tap` is a lossy
subscription: `Log` offers each event to its buffered channel (4096)
with one non-blocking send under the lock it already holds, and an event
that does not fit is counted, never waited for; unlike an SSE
subscriber, a tap that falls behind is not closed. `internal/observe`
runs the handlers on its own goroutine, ticks them every 5 s, and logs
`observe.dropped {dropped, total, buffer}` at most once per tick when
the tap overflowed. No config knobs: every limit is a constant.

### Event ids

Every line may carry two optional top-level fields that tie events
together, so a reader groups them by id instead of guessing by time:

- `utterance_id` — one user utterance. The relay mints it as it claims
  the user's words (`supervisor.relay`, `relay_fallback`,
  `relay_by_daemon`); `supervisor.relay` also carries
  `waited_ms`, from the input's last fragment to the relay. The orchestrator
  turn that answers it (`brain.Request.UtteranceID`), `brain.reply_*`,
  `supervisor.utterance_coalesced` and the reply push (tag
  `utterance_id`, so `voice.push`, `voice.push_held` / `_released` /
  `_dropped` / `_unheard`) carry it, and so does a spoken inline result
  (`voice.ToolResult.UtteranceID`, never sent to the model). The voice
  session tags the first `voice.playback {state: started}` after it
  handed such a reply to the model with its `utterance_id`.
- `turn_id` — one orchestrator turn (`turn-<run>-<n>`, unique across daemon
  runs). A decorator on the orchestrator's logger stamps every event that
  carries the turn number (`brain.step`, `brain.tool_call`,
  `brain.tool_result`, `brain.tool_timeout`, `brain.failover` of a turn's
  step, `brain.yielded`, `brain.fallback`, `brain.turn`,
  `brain.compaction`, `brain.transcript`, `context.step`) with the turn's
  `turn_id` and `utterance_id`. `brain.turn_started` marks the turn lock
  taken (`queue_ms`, `budget_ms`); an announce turn's `brain.turn_started`
  and `brain.turn` carry the worker `event_id` it serves.

Both are lifted from the payload (`payload.turn_id`,
`payload.utterance_id`, when strings) exactly like `dur_ms`, so an
emitter sets them by adding a key, and they stay in the payload too.
Lines written before they existed have neither; the scorecard falls
back to the older links (`call_id`, `brain.reply_pending {id}`,
`answers_utterance`) and to time then.

### turn.latency

One line per user utterance (source `observe`), Pipecat's
`LatencyBreakdown`: the wait from the user's last words to the first
audio of the answer, cut into consecutive segments — `voice_ms` (last
words → the voice's `to_supervisor` call), `relay_ms` (→
`supervisor.relay`; for the daemon's own relay, its unanswered wait),
`queue_ms` (→ `brain.turn_started`), `brain_ms` (→ `brain.turn`) with
`steps_ms` (each `brain.step`), `model_ms` and `tool_ms`, `delivery_ms`
(→ the reply handed over: the `voice.tool_result` carrying it, or
`brain.reply_delivered` queueing the push), `push_queue_ms` (→
`voice.push`, sent to the model) and `first_audio_ms` (→
`voice.playback {state: started}`), plus `total_ms`, `relay`
voice\|daemon, `reply` tool_result\|push, `stale`, and `outcome`
played\|no_audio (handed over, no playback start within 30 s)\|silent\|dropped\|coalesced\|no_voice\|timeout (10 min)\|restart.
It is emitted when the reply starts playing or the record ends. The
reply's playback start is the one tagged with its `utterance_id`; in a
log from before the tag, the first start after the hand-over. `sheepdog scorecard` prints p50/p90 per
segment ("Turn latency") from these lines, or replays the raw events
through the same `Tracker` for a log recorded before them.

### Watchdog

Every 5 s the watchdog checks the daemon's long-lived parts, and only
observes — nothing is restarted or cancelled:

| component | miss when |
|---|---|
| `brain` | the running turn (`brain.RunningTurn`: `brain.turn_started` → `brain.turn`) is more than 30 s past its hard budget |
| `push_queue` | a push has waited more than 90 s while a listener is attached (held for want of one is normal: the wait counts from the attach) |
| `herdr` | the watcher has had no successful snapshot or event for three snapshot intervals (or no watcher runs); a socket ping, run off the tick, adds whether herdr itself answers |
| `voice` | the voice session's own stall detection says stalled (`EventStatus{Stalled}`, logged as `voice.stalled`) |

A miss logs `daemon.heartbeat_missed {component, age_s, detail}` once
per incident, and `daemon.heartbeat_ok {component, down_s}` when it
recovers.
