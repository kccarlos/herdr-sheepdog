## Decision: one decision-maker (D1-revised)

The split "voice model classifies intent into seven tools that
execute; SVP reasons" gave the weaker judge the side effects. The
assistant is excellent at hearing, speaking, timing and register, and
unreliable at judgment; the SVP already resolves intent correctly from
the transcript. So:

- The assistant has **two tools**: `to_supervisor(text)` — the CEO's
  words verbatim — and `stop()`. Small talk needs no tool. Everything
  that touches the world (`ask`, `propose`, confirm, promises, notes,
  status) is the SVP's call from the transcript, behind the existing
  `send_keys` rail (the CEO's verbatim words in the current turn, keys
  from the prompt's option set). `briefing`, `ask`, `propose`,
  `confirm`, `cancel`, `note` as voice tools are removed.
- The assistant may answer a **follow-up** from the most recent SVP
  reply's `detail`/`options` without going back (no side effect); anything
  else goes to the SVP. It repeats back when unsure it heard right.
- **Status questions** cost one SVP step: the request carries the roster,
  the cached briefing sentence and open promises, so "what's going on"
  is answered without a tool call (~1.3 s on DeepSeek).
- **Code fast paths** (deterministic, no model): a bare "yes"/"no"/
  "option two" while exactly one `answer_prompt` is open and within its
  TTL → keys (it is the CEO's verbatim word, so the rail is satisfied);
  a bare "stop"/"wait"/"cancel"/"no no" → the stop procedure below. Bare
  = the whole utterance, so "don't stop the tests" never matches.
- Pushes cannot become cues: the assistant has nothing to answer them
  with; a spoken "yes" reaches the SVP next to the push in its transcript.
- Cost: one SVP call per utterance; DeepSeek (or a billed Gemini project)
  is the practical default brain — the free tier will not carry it.

## Decision: stop is a procedure in code

"Stop" means something different per phase; the supervisor knows the
phase from state it already has, so no model decides *what* to stop:

1. Assistant call not yet handed over → drop it.
2. SVP CEO-turn in flight, no write tool executed → cancel the turn's
   context (write tools run under it and never execute); record
   "CEO said stop; request *X* withdrawn before anything was sent".
3. An instruction was sent to a worker within `supervisor.cancel_window_s`
   (30 s) and it is `working` → `interrupt(agent)` (Ctrl-C; Codex aborts
   the turn and stays alive; the fake finish is already suppressed).
4. An open `answer_prompt` is left open — stop is not "no"; the CEO
   decides.
5. Then one short SVP turn: say what was stopped, offer the correction.

Not attempted: undoing worker edits automatically (that is an
instruction to the worker — "revert what you just did" — a normal SVP
turn) or a send delay to make stop easier. `stop()` stays an assistant
tool because it is time-critical and a false positive is cheap; the
bare-utterance fast path runs in code before the model even returns.
Event turns (announce) are not cancelled by stop. Every stop is logged
(`supervisor.stopped {phase, what}`) and shown on the Conversation view.

## Decision: nothing interrupts the assistant mid-sentence except the CEO

The daemon tracks "assistant speaking" (an open turn with
`voice.transcript.out` flowing). While speaking, any push or tool result
scheduled INTERRUPT is downgraded to WHEN_IDLE, except a due promise or
a `needs_user` decision on a *new* block. An SVP addition to a block is
dropped when the block's pending action is no longer open; if it lands
within `brain.announce_wait_s` it replaces the template line instead of
following it; otherwise it is queued `idle`. One `voice.push_deferred`
event per downgrade.

## Decision: blocked → blocked is a block

After keys are sent to a blocked pane, poll it for ~10 s (1 s cadence):
still `blocked` with a prompt different from the answered one → a
synthetic `blocked → blocked` transition (new pending, new push). A
reconciler on the 30 s snapshot does the same whenever state is
`blocked`, no pending is open and `last_block.answered` — this also
covers prompts that appeared while the daemon was down. `briefing`
composes "asking …" from the live pending, so the cache is right by
itself.

## Smaller items

- A promise persisted from an earlier daemon run is spoken once at
  startup ("still watching for …"), not appended to every briefing.
- A status answer repeated within 60 s with no state change says "no
  change since I last checked".
- Verify #27's "check again → fresh look" in the first session; under
  D1-revised the SVP decides it anyway.

## Prompts under the new structure

The persona stays: warm, unflappable, proactive, pleased to work with
(#27). The assistant prompt shrinks to: persona, hearing (repeat back
when unsure), the two tools, follow-ups from the last reply, pushes
(say at once, then the next step — never act on them), no facts of its
own. The SVP prompt absorbs the intent guidance the assistant had
(status vs question vs instruction vs confirmation vs promise, with the
CEO's words as the request), keeps the Manner section (#27), and gains:
its block line names the decision and never says "say yes"; a request
of the kind "yes" is answered through `send_keys` only under the rail,
else it asks. Evals: the assistant routing set becomes "relayed
verbatim"; `svp.jsonl` grows utterance → expected tools cases.

## Decision: explanations are investigations, not turns

The CEO cannot see the screen, so "explain what happened", "why did it
fail", "what does that mean" are first-class requests. Today they hit
two limits that are right for status and wrong for explanation: `spoken`
is two sentences, and a CEO turn falls back to the template after ~8 s.

- **Register.** For an explanation request the SVP answers in a short
  spoken paragraph ordered for the ear — what happened → why → what it
  means for the CEO → the next move — plain words, no identifiers,
  jargon only if the CEO used it first. Depth is layered and the SVP
  picks the cheapest layer that answers: the last reply's `detail`
  (the assistant answers this one itself, instantly), a screen read
  (~2 s), the record (`recall`), then an investigation. After a failure
  or a surprising finish the SVP *offers* the explanation ("want me to
  dig into why?") rather than volunteering the paragraph.
- **No time limit on the answer; a limit only on the acknowledgement.**
  An investigation has no wall-clock budget and no step budget beyond a
  sanity ceiling (`brain.investigate_max_s`, 10 min) so a stuck job dies;
  what is bounded is the SVP's first reply: within the ask budget it
  says what it is doing and roughly how long ("reading the diff, about
  half a minute", `pending: true`).
- **The investigation is a background job, so the SVP stays free.** It
  does not hold the turn lock for a minute while a worker blocks or the
  CEO asks something else. The SVP's tool `investigate(agent, question)`
  starts a job and returns its id; the job runs the existing read-only
  CLI query (`codex exec` / `claude -p` in the worker's repository — an
  agent with real context, sandboxed read-only) or, when the worker is
  idle, asks the worker itself in its pane (it has the best context; never
  while it is working, since a prompt would interrupt it). One job at a
  time; a newer investigation about the same agent replaces a queued one.
  `run_cli` as a synchronous tool remains for short lookups.
- **Delivery is an event turn.** The job's result is ingested as
  `investigation.done` and handled like a worker event: an SVP event
  turn (read tools only, existing queue/yield/coalesce rules) composes the
  explanation from the transcript, the request and the result, and pushes
  it `idle` tagged with the request it answers — the CEO is expecting it,
  so it waits for a pause and never interrupts. "Anything yet?" is
  answered by the assistant from the open-request state without a turn.
- **Follow-ups keep the sub-agent's context.** The CEO will ask again
  ("I still don't get it", "but why does that guard exist?"). The first
  follow-up is usually answerable from the raw result already in the
  window (or on disk via `recall`); a deeper one resumes the *same*
  CLI session — `investigate(follow_up_of=job, question)` — using the
  harness's own session persistence (`codex exec` resume by id,
  `claude -p --resume`; verify flags at implementation time). The
  harness is the persistence layer: no mailboxes, no long-lived
  sub-agent processes, no sub-agent transcript in the SVP's window. The
  SVP keeps a small investigation ledger `{job, agent, question,
  session id, summary, when}` searchable by `recall`; sessions expire
  after `brain.investigate_session_ttl_s` (1 h). One live investigation
  per agent. An answer from a resumed session after the worker has
  worked since is prefixed "as of a few minutes ago".
- **Stop applies.** A stop or a new request about the same thing cancels
  the job (stop procedure phase 2); every job is logged
  (`investigation.started/done/cancelled {id, agent, dur_ms, source}`)
  and the Conversation view links acknowledgement and answer.
- Config: `cli.timeout_s` no longer bounds investigations
  (`brain.investigate_max_s` does); `brain.ask_timeout_s` stays the bound
  on the acknowledgement.

## Backlog: `recall` is the memory seam

`recall(query)` is a bag-of-words search over the ledger (last result /
task / question per agent, notes, promises) and the on-disk transcript,
top 8 lines by word overlap, newest on ties. It has no ids and stores
nothing under a query; its weakness is phrasing ("that database thing"
vs "IndexedDB late-binding"). Acceptable while the record is small and
the recent transcript is in the window. When the investigation ledger
lands and the record grows, upgrade it in place — same tool signature —
to semantic search over the same sources plus investigation summaries,
and make it the plug point for the memory system (plan P6): memories
are recalled through this tool, so nothing above it changes. Not before
word search actually fails in a session.
